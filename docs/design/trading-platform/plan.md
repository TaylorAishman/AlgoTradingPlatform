## 2. How to read the task table

- **Files** is the ticket's scope: a task creates or changes only the paths in its Files cell. The acceptance tests that `requirements.md` names for a task's requirements are written in the listed test files under exactly those names.
- **Proof** runs inside the environment that J01's proof creates (`.venv`, Python 3.12) and uses shell brace expansion (bash or zsh). Every proof starts with the four default checks of R-246 to R-249, because `.devteam/verify.sh` is leaving the workflow (RQ1) and the proof is then the only check a ticket carries. The second `pytest` call names the tests the task must add, so the proof fails when one is missing.
- **Reqs** lists the requirements a task satisfies. Three notations follow a semicolon. `part of R-x`: the task builds part of the behaviour and another task holds the acceptance test. `enabling work for R-x`: the task satisfies no requirement by itself and exists so that the named ones can be built independently. `withdrawn: R-x`: see section 6. For these three notations the requirement's acceptance check is not part of the task's definition of done; the Proof cell is.
- **Depends on** lists direct dependencies. Some exist only to order writes to one file: `requirements.md` fixes the test file names, and several files hold many requirements (`tests/validation/test_gates.py` holds 20, `tests/execution/test_risk_gate.py` 16, `tests/e2e/test_paper_jobs.py` 14). Tasks that write the same file are chained. This is why components G, H and J have long chains.
- Tasks were cut to stay near 400 changed lines including tests. The largest rows by that estimate are A02, B15, B16, E03, G04 and J15.
- A row that names several behaviours is still one change to one module. Behaviours were kept in one row only where they share a module and a test file and splitting would have lengthened a chain without making either part easier to review (for example H15 and H19, two gates each). PQ-7 asks whether that is acceptable.

Rules for every task:

1. Package `__init__.py` files are created empty by J01 and never edited. Modules are imported by full path, which matches the dotted-path rule of Arch D22.
2. No task adds a `conftest.py`. The root `tests/conftest.py` is written by J01 and extended once by B04.
3. Settings of one implementation are validated by that class's own `Params` model (PL-7), so no task after A10 edits `src/atp/core/config.py`.
4. A task whose proof exposes a defect outside its Files stops and reports it (CLAUDE.md: "Stay inside the ticket's Scope"). This matters most for the tasks whose Files are tests only (C13, F16, G15, J02, J25, J27, J29, J30, J31).
5. Tests use only the generator of A11 to A13 and symbols from the reserved list of A06 (R-282). No task commits market data, news text or keys (R-281).
6. Three exceptions to the ownership table of Arch 4: J01 creates the empty package files of every component and the root `tests/conftest.py`; B04 extends that file; F15's test sits in `tests/e2e/` because R-144 names it there. PL-6 covers A04 and A05.

## 8. Open questions

- **PQ-1. Toolchain before wave 1.** R-244 and J01's proof need Python 3.12. This machine has 3.9 (system) and 3.15 only, and no `ruff`, `pytest` or `mypy` on the `PATH`. Will the owner install 3.12, or change the pinned version (Arch Q1)? Also still to be done by a human: delete `.devteam/verify.sh` and its CI step (RQ1), and decide whether CI runs the four default checks (RQ23). The kit's Stop hook runs the script wherever it exists; in this working tree it would fail once `pyproject.toml` exists and `ruff` and `pytest` are not on the `PATH`. The kit's implementer agent and its ticket template also tell agents to run the script.
- **PQ-2. How build agents read the papers.** The PDFs are ignored by git (R-314), so an implementer working in a fresh worktree has no copy; the plain-text copies used for the design stages sit in a temporary directory and garble equations; and this machine cannot render PDFs. C04, E02, E03, E04, H04 and H05 implement formulas that the requirements cite by page. Options: (a) keep the PDFs and text copies at a stable local path and name it in those tickets; (b) add a tracked `docs/design/trading-platform/formulas.md` in which a human transcribes and checks the formulas and worked examples those tasks need, which would also close RQ2. Which?
- **PQ-3. Paper-account probes.** Who runs the `alpaca` checks of G15, and when? The fixtures of B13, B14 and G11 are hand-written from behaviour Alpaca's documentation leaves open (R-181, R-290, R-296). The plan assumes the owner runs the probes once G15 is merged and files one ticket per difference before the first paper session.
- **PQ-4. Interface additions.** Confirm PL-1 to PL-5, PL-7 and PL-10 to PL-12 of section 3. They add four methods or fields to the protocols of Arch 5, a third argument to `evaluate_gates`, a `[data]` configuration section, a `role` key, a rule for commands without `--config`, and a deliberate point-in-time exception for one ablation.
- **PQ-5. Content of `configs/paper.toml`.** The requirements fix only its risk limits (R-313). The plan assumes the default pipeline of R-152: `tsmom` and two characteristics, the factor risk model, `MarkowitzAllocator`, long-only, whole-share `opg` orders. Confirm or name another. J12 also ships the three baseline configurations (equal-weight, inverse-volatility, time-series momentum) that R-215 requires a configuration to name; no requirement says where they live.
- **PQ-6. The optional plugin.** Build I01 to I07 with the rest, or hold them until RQ17 (provider, budget, alias dictionary) is answered? Nothing else waits for them.
- **PQ-7. Grouped rows.** Chains through shared test files were kept short by letting some rows carry several related behaviours (section 2). Strict one-behaviour rows would add roughly 20 tasks and lengthen the chains of G, H and J by a few waves (an estimate, not computed). Is the grouping acceptable?
- **PQ-8. Kit files are not committed.** `CLAUDE.md`, `REVIEW.md`, `.devteam/` and `.github/` are untracked in this working tree. An implementer in a fresh worktree and a reviewer reading the base branch will not see them, and no workflow is committed. Is that intended?
- **Open in `requirements.md`.** RQ2, RQ3, RQ5, RQ9, RQ10, RQ11, RQ14, RQ17, RQ18, RQ20, RQ21, RQ22, RQ23 and RQ24, and the assumed answers to the architecture's Q1 to Q13, are still open. Section 7 shows what each one moves.

This stage needs human approval before tickets are created.
