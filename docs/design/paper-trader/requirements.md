# paper-trader: requirements

Stage 2 of the design, built from `architecture.md` and `docs/reference/`. One table per component. "Arch" means `architecture.md`; "Brief" means `docs/reference/paper-trader-source-brief.md`; "Review" means `docs/reference/literature-review-for-builders.md`; "Decisions" means `decisions.md`.

How to read an acceptance check:

- Function and type names are the ones in Arch section 5. Paths are module paths, for example `pt_core::types::Symbol`.
- "The mock" is `pt_mock_alpaca::server::MockAlpaca`. "A loopback client" is `pt_alpaca::http::loopback_client(&mock.url())`.
- "The 2024 calendar" is every weekday of 2024 except 2024-01-01, 01-15, 02-19, 03-29, 05-27, 06-19, 07-04, 09-02, 11-28 and 12-25. It has 252 sessions, from 2024-01-02 to 2024-12-31.
- "The worked example" is defined once, under component K.
- Decimal results are compared as exact decimal values unless a tolerance is given. Floating-point results are compared within the stated tolerance, or 1e-9 if none is stated.
- No test may sleep, wait on the wall clock, or reach a host other than loopback.

## A. Core types (`pt-core`)

| ID | Requirement | Source | Acceptance check |
| --- | --- | --- | --- |
| R-010 | A symbol must be 1 to 12 characters from A-Z, 0-9 and `.`, starting with a letter. | Arch 5.1 | `Symbol::new("SPY")` and `Symbol::new("BRK.B")` succeed and `as_str` returns the input. `Symbol::new` returns `CoreError::InvalidSymbol` for `""`, `"spy"`, `"1ABC"`, `"SP Y"` and a 13-character string. |
| R-011 | A price must be strictly positive. | Arch 5.1 | `Price::new(dec!(0))` and `Price::new(dec!(-1))` return `CoreError::NonPositivePrice`; `Price::new(dec!(0.0001))` succeeds and `value()` returns 0.0001. |
| R-012 | A bar price received as a float must become the decimal that the float prints as, not its binary expansion. | Arch D-11 | `Price::from_f64_shortest(123.456789)` has value exactly 123.456789; `from_f64_shortest(0.1)` has value exactly 0.1; NaN and infinity return `CoreError::NotFinite`; 0.0 returns `CoreError::NonPositivePrice`. |
| R-013 | Rounding to six places must round midpoints away from zero. | Arch D-10 | `round6(1.0000005) == 1.000001`, `round6(-1.0000005) == -1.000001`, `round6(2.0000004) == 2.000000`. |
| R-014 | Notional must be exact decimal arithmetic on signed whole shares. | Arch D-10 | `Price::new(dec!(101.25)).notional(-3)` equals `Money(dec!(-303.75))`. |
| R-015 | An order intent must have a positive quantity and leg 1 or 2. | Arch 5.10.4 | `OrderIntent::new` with qty 0 returns `CoreError::InvalidOrder`; with leg 0 or 3 returns `CoreError::InvalidOrder`; with qty 5 and leg 2 succeeds. `Side::Buy.sign() == 1` and `Side::Sell.sign() == -1`. |
| R-016 | A cost specification must reject negative parameters. | Arch 5.10.5 | `CostSpec::zero()` has all four fields equal to 0 and validates. A `CostSpec` with any one field set to -1 returns `CoreError::InvalidCost` from `validate`. |
| R-017 | Order states must follow the transition table of Arch 5.1. | Arch 5.1; Review "Rust-first stack" | `transition_allowed` returns true for exactly these pairs: Intent to Submitted, Rejected, Abandoned; Submitted to PartiallyFilled, Filled, Canceled, Expired, Rejected; PartiallyFilled to PartiallyFilled, Filled, Canceled, Expired. It returns false for every other pair among the nine states, including every pair whose source is DryRun, Filled, Canceled, Expired, Rejected or Abandoned. |
| R-018 | The in-memory market view must never return data after the requested date. | Arch 5.1; Review "Backtesting methodology" | A `MemoryView` holding adjusted closes for symbol A on 2024-01-02, 01-03 and 01-04 returns two entries, oldest first, from `adj_closes(A, 2024-01-03, 10)`, and one entry (2024-01-03) from `adj_closes(A, 2024-01-03, 1)`. `exec_bar(A, d)` returns the bar pushed for `d` or `None`. `adv_shares(A, 2024-01-04, 2)` is the mean volume of the two latest pushed bars dated on or before 2024-01-04, and `None` if fewer than two exist. |
| R-019 | Time must be injectable. | Arch 5.1; Review "Rust-first stack" | `FixedClock(t).now_utc() == t` for a chosen instant; `SystemClock.now_utc()` returns an instant later than 2026-01-01T00:00:00Z. |

## B. Calendar (`pt-calendar`)

| ID | Requirement | Source | Acceptance check |
| --- | --- | --- | --- |
| R-020 | A calendar must be built only from a non-empty, strictly increasing list of dates. | Arch 5.2; Yin et al. 6.2 | `TradingCalendar::new(vec![])` returns `CalendarError::Empty`; a list with 2024-01-03 before 2024-01-02 returns `CalendarError::NotSorted`; a list with 2024-01-02 twice returns `CalendarError::Duplicate(2024-01-02)`. |
| R-021 | Next and previous session lookups must be strict and skip weekends and holidays. | Arch 5.2 | On the 2024 calendar: `next_session(2024-03-28) == Some(2024-04-01)`; `prev_session(2024-04-01) == Some(2024-03-28)`; `next_session(2024-03-30) == Some(2024-04-01)`; `next_session(2024-12-31) == None`; `prev_session(2024-01-02) == None`; `is_session(2024-03-29) == false`. |
| R-022 | A range query must be inclusive at both ends. | Arch 5.2 | On the 2024 calendar `sessions_between(2024-01-01, 2024-12-31)` has 252 entries and `sessions_between(2024-01-02, 2024-01-05)` has 4. A range with `from` after `to` is empty. |
| R-023 | The calendar must report calendar days to the next session. | Arch 5.10.5 | On the 2024 calendar `calendar_days_to_next(2024-03-22) == Some(3)`, `calendar_days_to_next(2024-03-28) == Some(4)`, `calendar_days_to_next(2024-01-02) == Some(1)`, and `calendar_days_to_next(2024-12-31) == None`. |
| R-024 | A session must count as a month end only when a later session in a different month is known. | Arch 5.2 | On the 2024 calendar `month_end_sessions(2024-01-01, 2024-12-31)` equals [01-31, 02-29, 03-28, 04-30, 05-31, 06-28, 07-31, 08-30, 09-30, 10-31, 11-29]; 2024-12-31 is absent because no later session is known. |
| R-025 | The month-end lookback must return the last session of the month k months earlier. | Arch 5.10.2 | On the 2024 calendar `month_end_back(2024-11-29, 1) == Some(2024-10-31)`, `month_end_back(2024-11-15, 8) == Some(2024-03-28)`, and `month_end_back(2024-11-29, 12) == None`. |
| R-026 | The monthly schedule must pair each month-end signal date with the next session. | Arch 5.2; Decisions "Order handling" | On the 2024 calendar `monthly_schedule(2024-01-01, 2024-04-30)` equals [(01-31, 02-01), (02-29, 03-01), (03-28, 04-01)]; a pair whose trade date falls after `to` is not included. |

## Out of scope

- Live trading of any kind: no live endpoint, no live key handling, nothing configurable to enable it.
- Intraday bars, real-time quotes, the `trade_updates` websocket, order-book data, limit orders, auction orders, extended hours.
- Options, crypto, single stocks, futures, fractional shares.
- Automatic handling of splits and other corporate actions in held positions during paper trading. A split shows up as a reconciliation break and halts the system.
- Dividends in the paper comparison. Paper does not simulate them.
- Locates and hard-to-borrow shorts.
- The AQR and Kenneth French replication targets.
- Parameter search, walk-forward optimisation, machine learning, LLM features and agents.
- HAR or other intraday-based volatility forecasts; covariance shrinkage; convex optimisation; partial rebalancing.
- Publishing the report anywhere. The owner copies from the local file.
- Python in any form.
- Changes to `.devteam/config`, `.github/workflows/`, `REVIEW.md`, `CLAUDE.md` and `docs/reference/`. The integrator updates `CHECK` and CI after the `workspace` chain lands (Arch 7.4).
